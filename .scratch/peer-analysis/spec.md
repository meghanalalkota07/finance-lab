# Peer Analysis: a second tab for multi-ticker sector/industry comparison

Status: ready-for-agent

Source: user request, refined over a full grilling session (universe scope, chart content, fundamentals-table scope, tab linkage, data-source and charting-library research, sector granularity — see `.scratch/peer-analysis/research/` for the two research reports this spec's data-source and charting-library decisions are drawn from). Renames the existing single-ticker page's implicit page to "Historicals" and adds "Peer Analysis" as a second tab. Builds on [Ticker Explorer v2's spec](../ticker-explorer-v2/spec.md) and the original [map](../ticker-explorer/map.md), which explicitly scoped "Multi-ticker comparison / overlay charts" out of v1/v2 — this spec is that reopened scope.

## Problem Statement

Today the app answers "how is this one company doing?" but not "how is this company doing *relative to its peers*?" A user researching a stock has no way to see its price performance or fundamentals stacked up against other companies in the same sector or industry without manually opening several browser tabs and eyeballing numbers across them.

## Solution

Add a second tab, "Peer Analysis," alongside the renamed "Historicals" tab. A user picks a GICS Sector (optionally narrowed to a Sub-Industry within it), selects up to 8 companies from that group via a multiselect, and sees: an interactive multi-line chart comparing their price performance over a custom date range (normalized % return by default, toggleable to raw price), summary performance stats (total return, volatility, max drawdown) per peer, and a fundamentals comparison table (one row per metric, one column per peer, cross-checked across the same four sources the single-ticker Fundamentals section already uses). Both the chart's plotted series and the full raw OHLCV behind it are downloadable as CSV.

## User Stories

1. As a user, I want the existing single-ticker page relabeled "Historicals" as a tab, so that it's clear it's one of two views rather than the whole app.
2. As a user, I want a new "Peer Analysis" tab next to it, so that I can compare multiple companies instead of researching one at a time.
3. As a user, I want to pick a broad sector (e.g. Technology) as my starting point, so that I can browse companies in an industry I care about.
4. As a user, I want to optionally narrow my sector choice down to a specific sub-industry (e.g. Semiconductors within Technology), so that I can compare more directly comparable peers instead of a whole broad sector.
5. As a user, I want to select specific companies from within my chosen sector/sub-industry via a search/multiselect, so that I control exactly which peers appear on the chart.
6. As a user, I want the number of companies I can select capped (at 8), so that the comparison chart's legend and colors stay legible instead of turning into visual noise.
7. As a user, I want the 5 largest companies (by market cap) in my chosen group pre-checked when I first pick or change a sector/sub-industry, so that I see a populated, useful chart immediately rather than an empty one.
8. As a user, I want Peer Analysis to open with a sensible default (Technology sector, top 5 pre-checked) before I've searched or picked anything myself, so that the tab isn't empty on first visit.
9. As a user, when I've already searched a ticker on the Historicals tab, I want Peer Analysis to start pre-seeded with that ticker's sector and that ticker pre-checked as a peer, so that I don't have to re-specify what I'm already looking at.
10. As a user, if the ticker I searched on Historicals isn't itself an S&P 500 company, I want Peer Analysis to just fall back to its own default selection rather than guessing at a sector match, so that I'm not shown a misleading or empty pre-selection.
11. As a user, I want the main visual to be an interactive multi-line chart, one line per selected peer, so that I can see relative price performance at a glance.
12. As a user, I want that chart normalized to % return (rebased at the start of my selected date range) by default, so that companies with very different share prices are visually comparable.
13. As a user, I want the option to toggle the same chart to show raw (unnormalized) price instead, so that I can also see actual price levels when that's what I want.
14. As a user, I want the same custom date-range controls (quick presets plus a custom start/end picker) that Historicals already has, so that the interaction feels consistent across tabs.
15. As a user, when my selected peers have different listing histories (e.g. a recent IPO alongside a decades-old incumbent), I want the chart to show as much history as is available for each — newer peers' lines simply starting later — rather than truncating every peer down to the newest one's start date.
16. As a user, I want to see summary performance stats (total return %, volatility, max drawdown) per peer for my selected date range, so that I have numeric comparison points alongside the visual chart.
17. As a user, I want a fundamentals comparison table showing one row per metric and one column per selected peer, so that I can compare things like market cap, P/E, and dividend yield across companies side by side.
18. As a user, I want each peer's fundamentals numbers cross-checked across the same sources (yfinance, SEC EDGAR, Finnhub, Alpha Vantage) the single-ticker Fundamentals section already uses, picking whichever source has data first in a fixed priority order, so that one source's gap or outage doesn't leave a peer's column blank.
19. As a user, I want a metric a given peer has no data for anywhere to show a clear placeholder rather than a blank or zero, consistent with the existing single-ticker pivot table's behavior.
20. As a user, I want to download the exact data behind the chart (normalized-or-raw series, one column per peer) as CSV, so that the download matches what I'm looking at.
21. As a user, I want a separate, more complete CSV download of full raw OHLCV for every selected peer, so that I have the underlying detail available even when it doesn't match the chart's current display mode.
22. As a developer maintaining this app, I want the sector/industry constituent list fetched live and cached (like the existing SEC ticker directory), so that S&P 500 membership stays reasonably current without a manual data-refresh step.
23. As a developer, I want a single ticker's failed historicals fetch to drop just that peer from the chart (with the rest still rendering), not fail the whole Peer Analysis view, consistent with this app's existing per-source/per-call graceful degradation philosophy.
24. As a developer, I want the peer fundamentals pivot to reuse the existing single-ticker `build_fundamentals_pivot` function internally rather than re-implementing per-source fetch/shape logic, so that the two features can't drift apart in how they read each source.
25. As a developer, I want all new data-fetching and data-shaping logic added to the existing `ticker_data.py` module (kept Streamlit-free), consistent with the project's existing single-data-service-module pattern, rather than splitting into a new module.
26. As a developer, I want the chart rendered with Plotly, consistent with every other chart in this app, rather than introducing a second charting library, so the app keeps one rendering stack and visual language.

## Implementation Decisions

- **Tabs**: `st.tabs(["Historicals", "Peer Analysis"])`. The existing single-page content (hero price line, Historicals section, Fundamentals section) becomes the "Historicals" tab's content, unchanged in behavior. The ticker search bar (and its sticky positioning) stays global chrome above the tabs, since Peer Analysis needs to read the currently-searched ticker to pre-seed itself.
- **Sector/industry data source**: a new `load_sp500_constituents() -> list[dict]` in `ticker_data.py`, fetching the `datasets/s-and-p-500-companies` GitHub raw CSV (`Symbol, Security, GICS Sector, GICS Sub-Industry, CIK`, among other columns), shaped to `{"ticker", "name", "sector", "sub_industry", "cik"}` per row (CIK zero-padded to 10 digits, matching `load_company_tickers`'s existing convention so it plugs directly into `get_fundamentals_history`). Fetched live and cached via `st.cache_data` in `app.py` at roughly the same TTL as `load_company_tickers` (24h) — no bundled/committed static snapshot. A fetch failure degrades the same way the existing ticker directory failure does (plain error state, tab unusable until it succeeds), no fallback source.
- **Sector picker UI**: two dependent selects — a Sector dropdown (11 GICS sectors) and an optional Sub-Industry dropdown scoped to the chosen sector's own sub-industries (an "All" option keeps it at the whole sector). Changing either resets the peer multiselect to that group's top 5 by market cap.
- **Peer multiselect**: standard multiselect over the chosen group's constituents (ticker + company name), capped at 8 selections (reject/ignore further picks past the cap, or disable remaining options — implementer's choice of Streamlit idiom). "Top 5 by market cap" for pre-checking is computed by fetching each candidate's `market_cap` via the existing `get_fundamentals_snapshot` (yfinance) and sorting — same source and shape as `_SNAPSHOT_FIELDS["market_cap"]` already uses.
- **Historicals→Peer Analysis linkage**: on first render of the Peer Analysis tab per session, if the currently-searched Historicals ticker is present in `load_sp500_constituents()`'s result, pre-select its sector (and sub-industry) and pre-check that ticker as one of the (up to 5) initially-selected peers. If it isn't present in the S&P 500 list, Peer Analysis falls back to its own independent default (Technology sector, top 5 pre-checked) with no attempt at fuzzy/sector-text matching.
- **Multi-ticker historicals fetch**: new `get_multi_ticker_historicals(tickers, start, end, *, fetch_historicals=get_historicals) -> dict[str, pd.DataFrame]` in `ticker_data.py`. Calls the existing `get_historicals` once per ticker; a per-ticker exception is caught and logged, and that ticker is simply omitted from the returned dict rather than failing the whole call. `app.py` diffs the requested tickers against the dict's keys to show a small note listing any peers that couldn't be loaded.
- **Price frame shaping**: new `build_peer_price_frame(histories: dict[str, pd.DataFrame]) -> pd.DataFrame` in `ticker_data.py` — pure reshape, no I/O. Produces a wide DataFrame indexed by Date, one column per ticker holding that ticker's `AdjClose`. Peers with shorter histories simply have `NaN`/absent rows before their first available date — no truncation of other peers' ranges to match.
- **Performance stats**: new `compute_peer_performance_stats(price_frame: pd.DataFrame) -> pd.DataFrame` in `ticker_data.py` — pure computation over the same wide price frame (restricted to the user's selected date range before calling), one row per ticker, columns for Total Return (%), Volatility (%, annualized standard deviation of daily returns), and Max Drawdown (%, peak-to-trough decline within the range).
- **Chart normalization and rendering**: stay in `app.py`, alongside the existing `price_chart`/`sparkline` figure builders — a small helper rebases each column of the price frame to % change from its own first available value in the selected range (not a shared start date across all peers, given uneven histories), feeding a multi-trace `go.Scatter` figure. A segmented control or radio (mirroring the existing Line/Candlestick control's styling) toggles between this normalized view and a raw-price view of the same underlying frame. `hovermode="x unified"`, default Plotly legend click-to-toggle, and `rangeslider_visible=True` are used for the interaction requirements — all native Plotly config, no new dependency.
- **Date range controls**: reuse the existing `DATE_RANGE_OPTIONS`/custom `st.date_input` pattern from the Historicals section, scoped to Peer Analysis's own widget keys. The range's usable minimum is the *earliest* available date across all selected peers' available histories (i.e. as far back as any peer goes), not the latest-listed peer's start — consistent with the "peers just start later" decision.
- **Fundamentals comparison table**: new `build_peer_fundamentals_pivot(tickers, cik_by_ticker, histories, *, fetch_snapshot=get_fundamentals_snapshot, fetch_history=get_fundamentals_history, fetch_finnhub=get_fundamentals_from_finnhub, fetch_alpha_vantage=get_fundamentals_from_alpha_vantage) -> pd.DataFrame` in `ticker_data.py`. For each ticker, calls the existing `build_fundamentals_pivot(ticker, cik_by_ticker.get(ticker), histories[ticker], fetch_snapshot=..., fetch_history=..., fetch_finnhub=..., fetch_alpha_vantage=...)` to get that ticker's metric×source table, then collapses each metric row to a single value by trying columns in priority order — yfinance, then SEC EDGAR, then Finnhub, then Alpha Vantage — taking the first non-placeholder value found. Output is one row per `_PIVOT_METRICS` entry (reusing that existing list/labels), one column per peer ticker. Alpha Vantage's existing 25-requests/day cap is shared app-wide (including with the Historicals tab's own Fundamentals section) and is not specially rationed or reserved for this table — once exhausted, Alpha Vantage values are silently omitted for the rest of the day, per the app's existing degrade-without-fallback philosophy.
- **CSV downloads**: two `st.download_button`s in the Peer Analysis tab — one for the currently-displayed chart series (whichever of normalized-% or raw-price is active, one column per peer, one row per date), one for the full raw OHLCV of every selected peer in long format (one row per ticker+date). Both reflect the app's existing pattern of building the CSV from an in-memory DataFrame (`.to_csv()`), not a new export mechanism.
- **Module placement**: all four new functions (`load_sp500_constituents`, `get_multi_ticker_historicals`, `build_peer_price_frame`, `compute_peer_performance_stats`, `build_peer_fundamentals_pivot` — five, correcting the count) live in `ticker_data.py`, kept free of Streamlit imports exactly like the module's existing functions. `app.py` wraps the I/O-touching ones (`load_sp500_constituents`, `get_multi_ticker_historicals`, `build_peer_fundamentals_pivot`) in `st.cache_data`, mirroring the existing caching block at the top of `app.py`.
- **Charting library**: Plotly, unchanged from the rest of the app. Confirmed via research (`.scratch/peer-analysis/research/02-charting-library-comparison.md`) that no evaluated alternative (`streamlit-echarts`, `streamlit-lightweight-charts`, Bokeh/`streamlit-bokeh`) offers a capability this feature needs that Plotly lacks, and two of the three have real currency/maintenance problems today.
- **Theming**: Peer Analysis reuses the existing Aurora theme constants (`AURORA`, `CHART_FONT`) and CSS classes (`.te-group-title`, `.te-note`, etc.) already defined in `app.py` — no new visual language introduced for this tab.

## Testing Decisions

- Same seam philosophy as the rest of `ticker_data.py` (confirmed in prior specs): test pure fetch/shape functions directly, never by mocking `ticker_data.py`'s own functions from within itself, and never through Streamlit.
- `load_sp500_constituents`: tested via `requests-mock` against the GitHub raw CSV URL, same style as `load_company_tickers`'s existing tests — cover a normal response and a malformed/unreachable one.
- `get_multi_ticker_historicals`: tested by injecting a fake `fetch_historicals` (the existing `fetch_historicals=get_historicals` parameter exists specifically for this) that succeeds for some tickers and raises for others, asserting the failing ticker is omitted and logged rather than the whole call raising.
- `build_peer_price_frame` and `compute_peer_performance_stats`: pure functions, no mocking needed at all — tested directly against small hand-built `DataFrame`s covering even histories, uneven/staggered start dates, and (for the stats function) a known-answer case (e.g. a simple monotonic series with a hand-computed expected drawdown).
- `build_peer_fundamentals_pivot`: tested by injecting fake `fetch_snapshot`/`fetch_history`/`fetch_finnhub`/`fetch_alpha_vantage` per ticker, the same pattern `build_fundamentals_pivot`'s existing tests already use, extended to confirm: (a) the priority-order fallback picks the right source when more than one has a value for the same metric, (b) a metric with no source coverage for a peer renders the placeholder, and (c) one ticker's total fetch failure doesn't blank out other peers' columns.
- The uneven-history behavior (peers starting later rather than the range truncating to the shortest) is easy to accidentally invert later — worth an explicit regression test once built, similar to the existing note about the Historicals CSV preview/download ordering split.

## Out of Scope

- Any universe beyond the S&P 500 (e.g. small/mid-caps outside the index, non-US listings). Revisiting this means reopening the sector-data-source research (`.scratch/peer-analysis/research/01-sector-data-sources.md`), which found no free option beyond a rate-limited live screener for broader coverage.
- Automatically reconciling disagreeing fundamentals sources into one "best" figure beyond the fixed priority-order fallback — no confidence scoring, averaging, or outlier detection across sources.
- Cross-sector peer comparison (comparing companies from different sectors/sub-industries against each other in one view) — the picker is always scoped to one sector (optionally one sub-industry) at a time.
- Correlation matrices, beta calculations, or any statistic beyond total return/volatility/max drawdown.
- Intraday granularity — daily bars only, consistent with the rest of the app.
- Persisting a user's peer selection across sessions or page reloads.
- A second charting library — Plotly only, per the research findings.

## Further Notes

- This spec introduces domain terms not yet reflected in the repo's root `CONTEXT.md` (currently states "no multi-ticker comparison" under its "Ticker" definition) — "Peer," "Peer set," "Sector," and "Sub-Industry" should get a domain-modeling pass alongside or shortly after implementation so `CONTEXT.md` stays accurate.
- The fundamentals-table collapsing rule (fixed source priority order: yfinance → SEC EDGAR → Finnhub → Alpha Vantage, first non-placeholder wins) is this spec's own synthesis of the grilling session's "multi-source cross-check, like the single-ticker pivot" decision, adapted to a peer-column layout instead of a source-column layout (a literal metric × (peer, source) grid was judged to sprawl too wide to be usable for up to 8 peers × 4 sources). If a genuine per-peer, per-source disagreement view turns out to matter more than this spec assumed, that's the most likely place to revisit.
- Two prior specs' explicitly-scoped-out decisions are reopened here: the original map's "Multi-ticker comparison / overlay charts (single ticker only for v1)" and v2's implicit single-ticker-only Fundamentals pivot shape. Neither is being silently overridden — both are addressed directly by this feature.
- Before this ships, no new API keys are needed — Peer Analysis reuses every credential (`FINNHUB_API_KEY`, `ALPHAVANTAGE_API_KEY`) and keyless source (yfinance, SEC EDGAR, the new GitHub CSV) already in place.
